# Agent Rules

- Proceed carefully.
- No DB work ever.
- No unit tests ever.
- After changes, run `npm install` (if dependencies changed) and `npm run build`.
- Do not use Laravel Mix; use the Vite-based build (`npm run build`) only.
- After changes that affect runtime behavior, run `php artisan optimize:clear`.
- Every landing-page build or update must include all three shared layers in this order: `resources/views/partials/breadcrumbs.blade.php`, `resources/views/partials/landing-hero.blade.php`, then `resources/views/partials/hero-meta.blade.php`. This applies to home, offering/category/modality pages, location pages, and SEO landing variants.
- Use the shared landing hero for every landing page. Use its general two-column treatment for category/modality and other non-location pages; when a landing page has a resolved location, pass `heroImage` and `heroLocationLabel` and `heroIsLocation => true` so it uses the location-image treatment. Do not create a page-specific landing hero without updating this shared partial and this rule.
- Landing-page hero metadata must render through the shared `resources/views/partials/hero-meta.blade.php` partial immediately below the hero, never as chips to the right of breadcrumbs. Use truthful metadata such as `Local listings`, `Nearby options`, and `Online sessions`; use the supplied dot/strong treatment for the first item and preserve responsive horizontal scrolling for additional metadata.
- Keep the landing stack continuous: do not add parent top padding or margins between breadcrumbs, the shared hero, and `hero-meta`; page-specific wrappers must start at the hero edge.

## Shared component catalogue

- `resources/views/partials/breadcrumbs.blade.php`: use on every landing page directly before the hero. Pass the real hierarchy and use icons only for Home, offering pages, and location pages; do not hand-build breadcrumb markup or add a second breadcrumb trail.
- `resources/views/partials/landing-hero.blade.php`: use for every landing-page hero. Pass copy, actions, and resolved location image data through its parameters; use the location treatment for location-resolved pages and the general two-column treatment elsewhere.
- `resources/views/partials/hero-meta.blade.php`: use immediately below every landing hero for truthful availability/context signals. Pass metadata as data, not as custom chips or breadcrumb content.
- `resources/views/partials/wow-button.blade.php`: use whenever a reusable link/button is needed in a Blade component. Select `primary`, `outline`, `soft`, `link`, `text`, `card`, or `icon` through the shared variant and size parameters; do not duplicate button CSS in a page partial.
- `resources/views/partials/modality-board.blade.php`: use for image-led modality collections on home, category, and location pages. Pass API-ranked modality items, location-specific URLs, counts, copy, and images; do not replace it with plain category tiles.
- `resources/views/partials/offering-tabs.blade.php`: use when a landing page has the three related offering collections local/current, new, and online. Pass all three collections and their labels/copy; the partial owns tab accessibility, active-panel switching, carousel controls, and the offering rails. Do not rebuild tab JavaScript or inject hand-written card markup in the page.
- `resources/views/partials/product_card_v4_1.blade.php`: use for every catalogue offering, including therapy, class, workshop, event, retreat, store product, search, recommendation, homepage, category, modality, and location rails. Keep the whole-card link, badges, behavioural ordering, and v4.10 responsive contract intact.
- `resources/views/partials/offering-button.blade.php`: use only for catalogue-card CTAs rendered by the v4.10 card. It selects `VIEW & BOOK`, `VIEW PRODUCT`, `BUY GIFT CARD`, or `VIEW` according to the offering state; never recreate the CTA inside a card or use a general landing button there.
- `resources/views/partials/location-explorer.blade.php`: use for nearby/location discovery tiles below a page’s primary offering content. Pass backend discovery records, canonical paths/URLs, images, and supply counts; the partial owns the full-width tile grid and borderless link actions. Do not add a `.container-page` wrapper, hardcode towns, or add a separate Browse-all button.
- `resources/views/partials/guides-section.blade.php`: use for guide collections on modality, offering, and location landing pages. Pass the section copy and guide links; use its shared collection CTA and borderless card links instead of rebuilding guide cards or buttons. Keep the section background and borders controlled by the shared partial.
- `resources/views/partials/popular-price.blade.php`: use for price-band discovery sections when backend data contains live price bands and counts. Pass the location, price-band records, and configurable copy; the partial owns the four-band responsive layout, featured popular band, canonical search URLs, counts, and price-card styling. Do not recreate price tiles in individual landing views or hardcode counts.
- Location landing modality/category sections must use the shared `resources/views/partials/modality-board.blade.php` component, the same image-led modality board used by the homepage. Pass the location-specific modality URLs, counts/descriptions, and available category images into that component; do not recreate the old plain modality tile grid.
- Location modality boards must pass the resolved location label to the Backend `/api/behaviour/discovery` request and use its location-scoped behavioural order for locally available modalities, with catalogue counts as the safe fallback. Do not use the global homepage discovery response for a location landing.
- Explore-location sections must use `resources/views/partials/location-explorer.blade.php`. Pass nearby location records from the backend discovery payload (`popular_places`/equivalent), including their canonical paths, images, and supply signals; never hardcode a list of towns or Mapbox results in the Blade partial. The partial accepts configurable eyebrow, heading, intro, featured item, and items, and its tile actions must use the shared borderless `partials.wow-button` link/arrow treatment. Do not add a standalone Browse-all button or page-specific button geometry to this component.
- Offering collections with local, new, and online variants must use `resources/views/partials/offering-tabs.blade.php`. Pass the three offering collections and configurable tab copy into the partial; render the canonical v4.10 offering-card partial inside each rail and keep tab/carousel behavior inside the shared component rather than rebuilding it on individual landing pages.
- Guide collection sections must use `resources/views/partials/guides-section.blade.php` with configurable copy and guide links. Use the shared outline/arrow `partials.wow-button` for the collection action and the borderless `btn-wow--link btn-arrow` treatment for card-level Read guide actions; do not recreate guide-section buttons or card markup in individual pages.
- All buttons must use the shared design system in `resources/css/wow-buttons.css` and the reusable `resources/views/partials/wow-button.blade.php` partial where a dynamic button is needed. Do not create page-specific button CSS or introduce Bootstrap button variants for storefront UI.
- Button variants are: `btn-wow--primary` for the single main conversion action; `btn-wow--outline` for secondary navigation and section-header actions; `btn-wow--soft` for optional/supporting actions; `btn-wow--card` only inside offering cards; `btn-wow--text` or the borderless `btn-wow--link`, normally with `btn-arrow`, for editorial/image-card links; and `btn-wow--icon` for recognisable utility controls, always with an accessible `aria-label`.
- Use `btn-wow--sm`, `btn-wow--md` (default), or `btn-wow--lg` for size. Use `btn-arrow` only when the action moves the user to another page, collection, or browsing state. Use `btn-wow--block` for full-width actions. Do not use square card buttons in heroes, breadcrumbs, navigation, or general landing sections.
- The same button system applies to navbar actions, breadcrumb actions, heroes, hero metadata controls, section headers, filters, cards, modals, checkout, and forms. Preserve one clear primary action per small area. Legacy `btn-wow--cta`, `btn-wow--ghost`, and `btn-sm` aliases may be maintained for migration, but new code must use the deck names.
- Section-header actions such as `View all`, `Browse online`, `Explore all`, and `Browse all modalities` must use `partials.wow-button` with an outline/arrow treatment. Offering/product cards must use `btn-wow btn-wow--card` (normally the primary `VIEW & BOOK` treatment) instead of custom card button classes; store cards use the same card variant. Editorial image-card links use `btn-wow btn-wow--link btn-arrow` or `btn-wow--text btn-arrow`; these link treatments must never have a border or glow.
- The shared button primitive owns its geometry and effects: never add page-specific `border-radius`, `box-shadow`, inset highlight, blue focus halo, or glow styles to a `.btn-wow`. The component radius is enforced for every variant (`pill` for normal buttons, `4px` for `btn-wow--card`, and borderless `0` for text/link actions); use the component class rather than legacy `.btn`, `.btn-sm`, `.btn-md`, or `.btn-lg` utilities for new markup.
- Offering cards use the shared v4.10 contract in `resources/css/offering-cards-v410.css` and `resources/views/partials/product_card_v4_1.blade.php` with `cardVersion => v4.10` during rollout. The separate `resources/views/partials/offering-button.blade.php` partial owns catalogue CTAs: use `VIEW & BOOK` for bookable offerings, `VIEW PRODUCT` for store products, `BUY GIFT CARD` for gifts, and `VIEW` for past events. Do not write CTA markup or button styling inside individual card renderers.
- v4.10 card sizing is fixed by viewport/context: 448px full desktop, 432px small desktop/tablet, 372px mobile; five columns at 1200px+, four columns from 992px to 1199px, three columns from 768px to 991px, and two columns on mobile below 768px. A compact landscape exception from 600px to 767px may use three cards when genuinely landscape; portrait/mobile layouts always use two cards per row. The same column contract applies to offering tabs, location grids, homepage rails, category/modality grids, search results, recommendations, and filters unless a component explicitly documents a different rail. Titles clamp to three lines, providers to two, descriptions show three lines at 768px+ and are hidden below 768px. Event/workshop/retreat cards use the full-image date-led treatment; therapy/class/store cards use the standard shell.
- In user-facing wellness copy, use “Modality” and “Modalities” instead of “Category” and “Categories.” Preserve technical field names, API keys, database columns, route parameters, and internal code identifiers unless a separate migration explicitly requires changing them.
